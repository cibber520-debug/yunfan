# 云帆志愿 App 后端架构提示词体系

| 项目 | 内容 |
|---|---|
| 版本 | V1.0 |
| 目标 | 让 AI 产出可实施、可量化、可评审的高性能、高并发、高可用后端架构方案 |
| 使用方式 | 先运行“系统角色提示词 + 项目上下文 + 总控提示词”，再按专项提示词深化，最后执行红队评审 |
| 适用阶段 | 架构设计、技术选型、容量规划、数据建模、API 设计、上线评审 |

## 1. 先定边界：这不是一句“帮我设计后端”

建议默认架构假设是：**CDN/WAF/API 网关 + 无状态业务服务水平扩容 + Redis Cluster 热点缓存 + PostgreSQL 主从/只读副本 + 消息队列削峰 + 独立推荐计算模块 + 离线数据管线 + 多可用区部署**。但必须要求 AI 对“模块化单体、服务化、微服务”给出量化比较，禁止为了高并发直接堆微服务。

建议演进路线是：MVP 采用“模块化单体（账户/画像/志愿表）+ 可独立扩容的推荐服务/Worker + 独立数据管线”；只有当团队边界、发布频率、资源隔离或实测瓶颈达到拆分阈值时，再拆服务。

以下容量值是**设计压测档位而非用户预测**：峰值 3,000 / 10,000 / 30,000 总 RPS 三档，不得等同于推荐接口 RPS；可用性目标 99.95%；引用数据与位次反查 p95 ≤ 100ms；缓存命中推荐 p95 ≤ 300ms；未命中推荐 p95 ≤ 1s、p99 ≤ 1.5s。草稿等已确认写入的多可用区目标 RPO≈0；区域灾难暂定 RPO ≤ 5 分钟、RTO ≤ 30 分钟。请求 SLO、可用区故障目标与区域灾难目标必须分别定义，正式方案必须用真实业务数据替换。

## 2. 运行前输入清单

将下列内容与 Prompt 0–2 一并交给 AI；缺失项必须在输出中标为假设，而非静默补全。

```text
INPUT_MANIFEST
- 需求与证据：文件/链接、版本、截至日期、owner、置信度
- 当前 API：OpenAPI 或 TypeScript 契约；未验证接口标“待验证”
- 实际变量：首发省份、注册用户、峰值 DAU、各接口峰值占比、突发曲线、后端团队、云平台、预算
- 数据样本：数据量、年份、省份、单行大小、更新频率、来源授权状态
- 现有基础设施：网关、数据库、缓存、消息系统、容器平台与监控
- 输出约束：先产主稿，再产专项附件；单次输出到达长度上限时停在完整章节末尾并列出未完成章节
```

## 3. 待替换变量

| 变量 | 含义 | 未知时处理 |
|---|---|---|
| `{{首发省份}}` | 首发覆盖省份 | 分“单省、5 省、全国”三档设计 |
| `{{注册用户/峰值DAU}}` | 用户规模 | 不可凭空猜测，输出假设区间 |
| `{{峰值RPS/并发连接}}` | 总负载与接口分布 | 使用 3k/10k/30k 总 RPS，并分别填写各接口占比与突发曲线 |
| `{{读写比}}` | 数据语义上的读写结构 | 不按 HTTP 方法判断；区分纯读、纯计算、持久化写 |
| `{{数据规模}}` | 院校、专业组、录取记录、一分一段数据量 | 给出估算公式和分区依据 |
| `{{云平台/机房}}` | 腾讯云、阿里云、私有云等 | 输出云中立组件与托管替代项 |
| `{{后端团队栈}}` | Java、Go、TypeScript 等 | 比较后再选，不默认拍板 |
| `{{预算}}` | 月预算和峰值临时扩容预算 | 分基础、标准、高保障三档 |
| `{{合规要求}}` | 个人信息、未成年人、等保等 | 默认按最小采集和高敏数据保护设计 |

## 4. 系统角色提示词（Prompt 0，置于最前）

```text
你是一名资深后端与云原生架构师，负责设计面向中国高考志愿填报场景的生产级系统。你的方案必须安全优先、数据准确优先、可观测、可压测、可回滚，并能应对“出分日至志愿截止日前”的短时洪峰。
工作原则：
1. 先区分【已知事实】【设计假设】【已作决策】【待确认问题】，不得把假设写成事实。
2. 先做容量模型和 SLO，再选技术；所有“高性能/高可用”必须转化为 RPS、延迟、错误率、资源量、RTO/RPO 和成本。
3. 同时比较模块化单体、服务化、微服务，默认选择满足目标的最简方案；说明何时必须拆分。
4. 关键链路不得同步扇出查询多个数据库；推荐请求应基于版本化只读数据快照、缓存或内存索引完成。
5. 对缓存穿透、击穿、雪崩、热 Key、重复提交、消息重复、数据库连接耗尽、节点宕机、可用区故障、数据版本错误逐一设计防线。
6. 输出正常路径、异常路径、降级路径和恢复路径；降级时绝不伪造录取结果或隐藏数据版本。
7. 所有写接口具备鉴权、参数校验、幂等、审计与一致错误格式；不得记录令牌、身份证件、完整手机号等敏感信息。
8. 架构图用 Mermaid；API、表、索引、缓存 Key、事件、告警和压测场景要具体到可交付工程团队。
9. 每项关键选型必须给出理由、替代方案、代价、触发升级阈值；禁止只列组件名。
10. 未经架构确认不要生成大段业务代码，先交付方案、ADR、风险清单与验收门槛。
```

## 5. 项目上下文提示词（Prompt 1，紧接角色提示词）

```text
项目：云帆志愿，高考志愿填报辅导 App。当前前端为 React 18 + TypeScript + Vite SPA，已通过服务适配器预留真实后端。
核心用户：考生；家长是决策/付费角色；教师端不在 MVP。
核心流程：省份与高考模式 → 分数反查省位次 → 选科与专项身份 → 院校/专业/地域偏好 → 权重 → 生成冲稳保垫推荐 → 组装志愿表。
现有前端契约：GET /api/v1/reference-data；POST /api/v1/rank-lookup；POST /api/v1/recommendations/generate。后续需补充登录、画像/草稿、志愿表、数据版本、符合选科的专业查询等接口。
核心规则：以省位次为跨年主键；按省份加载投档规则；选科和黑名单先硬过滤；结合历史录取位次、招生计划、等位分与风险偏好生成 REACH/MATCH/SAFE/CUSHION 四档；低数据质量必须展示置信度与来源；不可给出录取承诺。
核心数据（需求候选，最终以数据模型评审为准）：province_rule、score_segment、school、major、school_major_group、subject_requirement、admission_history、enrollment_plan、candidate_profile、preference、recommendation_run/result、volunteer_plan/item、data_version、audit_log。
流量特征（业务判断，须用埋点/容量数据验证）：全年低谷明显，但出分、批次线发布、志愿截止日前会突发洪峰；引用数据和位次反查是超高频读；推荐生成是 CPU/内存计算热点；草稿自动保存与志愿增删是高频小写；数据导入发布是低频大批量写。
正确性约束：同一次推荐必须绑定不可变 release_bundle_id，统一引用 data_version、algorithm_version、rule_version、schema_version、快照哈希和兼容矩阵；版本通过单一 active pointer 原子切换，旧结果必须可追溯并可回滚。
设计压测档位：3k/10k/30k RPS；读写比暂按 95:5；SLO 暂按可用性 99.95%、位次反查 p95≤100ms、缓存推荐 p95≤300ms、未命中推荐 p95≤1s/p99≤1.5s、RPO≤5min、RTO≤30min。以上均为假设，必须列出验证方法。
范围外：教师端、社区、录取承诺、完整博弈热度预测、真人专家履约；但架构应预留事件和服务边界。
```

## 6. 总控架构提示词（Prompt 2，首次完整出方案）

> 建议先要求 AI 输出 A–F“架构决策主稿”，确认后再继续 G–R“工程专项附件”，避免一次输出过长而浅化。

```text
基于以上角色与项目上下文，为该 App 设计后端总体架构。先提出不超过 12 个会改变架构的关键问题；对当前无法回答的问题给出明确假设，并继续完成方案，不要停在提问阶段。
必须按以下顺序输出：
A. 一页结论：推荐架构模式、技术栈候选、核心理由、MVP 与目标态差异。
B. 需求与 SLO：业务峰值窗口、接口分级、可用性、p95/p99、错误预算、RTO/RPO、数据一致性和合规目标。
C. 容量模型：按 3k/10k/30k 总 RPS，将流量分解到每个接口；分别列峰值占比、突发曲线、命中率、平均响应体、CPU-ms、服务时间分布、DB 查询数和连接占用。Little's Law 只用于估算在途并发，实例数必须由基准测试吞吐、目标利用率与安全系数反推；同时计算 Redis QPS/内存、消息吞吐和网络带宽。
D. 三方案比较：模块化单体、混合服务化、微服务，从性能、复杂度、团队规模、故障域、成本、发布和数据一致性评分，并选择一个方案。
E. 总体架构图：客户端、CDN、WAF、负载均衡/API 网关、业务服务、推荐计算、Redis、主库/只读副本、MQ、对象存储、数据管线、数仓/分析、可观测平台和第三方数据源。
F. 模块/服务边界：职责、拥有数据、同步 API、异步事件、扩缩容单位、依赖、超时、重试、熔断、幂等和故障降级；禁止共享表式伪微服务。
G. 核心调用链：引用数据、分数反查位次、推荐生成、草稿保存、志愿表编辑、数据版本发布，分别给出时序图和延迟预算。
H. 数据架构：ER 模型、表结构方向、主键、唯一约束、索引、按省份/年份分区、冷热分层、读写分离、连接池、迁移、备份和数据生命周期；用 release_bundle_id 管理不可变组合版本、请求租约、缓存命名空间、旧版本回收与回滚验证。
I. 缓存方案：浏览器/CDN/网关/Redis/进程内五级缓存适用边界，Key 设计、TTL、版本化、预热、互斥重建、随机过期、空值缓存、热点隔离、失效与一致性；区分可共享公共计算结果和用户私有 run/画像/草稿，严禁跨用户缓存泄露。
J. 推荐引擎：候选集离线预计算、版本化快照、在线硬过滤/打分/降级、公共请求指纹缓存、用户私有运行元数据、计算超时、异步化阈值、结果可解释性、可复现和回滚；覆盖同分位次区间、批次/投档模式、专业组代码跨年变更、征集志愿、专项计划、选科/体检/性别/语种限制、学费校区、服从调剂、临时计划更正和截止时间。
K. 数据管线：采集、校验、清洗、去重、规则校验、质量评分、影子发布、抽样核验、审批、原子激活和回滚；任何脏数据不得直接进入在线推荐。
L. 高可用与容灾：多可用区、无状态扩容、自动伸缩、限流、排队、熔断、负载保护、优雅停机、备份恢复演练；列出单点故障和 FMEA。
M. 安全与隐私：认证、RBAC/ABAC、未成年人和个人信息最小化、传输/存储加密、密钥轮换、防重放、防爬、防刷、WAF、审计、数据脱敏和删除机制。
N. 可观测性：OpenTelemetry trace、RED/USE 指标、业务正确性指标、结构化日志、request_id/recommendation_run_id/release_bundle_id 贯通、告警阈值和看板；高基数字段只进入日志/Trace，不得作为时序指标标签。
O. 交付与运行：环境隔离、容器/Kubernetes 或托管替代、IaC、CI/CD、数据库迁移、蓝绿/金丝雀、回滚、Feature Flag 和配置中心。
P. 测试：单元、契约、集成、数据质量、回放、压测、尖峰、浸泡、故障注入、容灾演练；给出通过标准。
Q. 成本与演进：基础/标准/高保障三档成本项，补充每次推荐、每万请求、每省每年数据的单位经济模型；给出 MVP→首发峰值→全国化三阶段路线与每阶段拆分触发阈值。
R. 最后输出 ADR 列表、Top 10 风险、待决策清单、90 天实施里程碑、可勾选验收清单，以及“需求→决策→风险→测试→证据”追踪矩阵。
禁止含糊表达：每个“使用缓存/限流/扩容/高可用”都必须说明位置、策略、参数初值、监控指标、失败行为和验证方法。
```

## 7. 专项深化提示词（按需逐条运行）

### Prompt 3：容量与峰值建模
```text
只深化容量规划。按参考数据、位次反查、推荐生成、草稿保存、志愿表编辑五类接口建立 3k/10k/30k 总 RPS 模型；不得把总 RPS 当作推荐 RPS。明确每接口峰值占比与突发曲线、缓存命中率、平均响应体、CPU 时间、DB 查询数、连接占用和服务时间分布。Little's Law 只估算在途并发；实例数必须用基准吞吐、目标利用率和安全系数反推。继续计算 Redis、数据库、MQ 和带宽；输出瓶颈顺序、自动扩缩容信号、预扩容时间点、拒绝策略和压测验收表。所有未知量必须显式列为变量并做敏感性分析。
```

### Prompt 4：领域边界与服务拆分
```text
基于 DDD 为账户与授权、考生画像、引用数据、位次服务、推荐引擎、志愿方案、数据发布、通知、审计分析划分限界上下文。输出上下文图、聚合与不变量、数据所有权、同步/异步契约和事务边界；给出 MVP 模块化单体目录，以及达到哪些量化阈值后拆出推荐/数据发布/账户服务。指出所有分布式事务，并优先用本地事务 + Outbox + 幂等消费者解决。
```

### Prompt 5：数据库与数据版本
```text
为核心实体设计 PostgreSQL 逻辑模型和关键 DDL 草案。必须包含主外键、唯一约束、检查约束、审计字段、软删边界、按 province_code + exam_year 的分区策略、查询对应复合/覆盖索引、EXPLAIN 验证计划、主从延迟处理和连接池预算。重点设计不可变 release_bundle_id，绑定 data/rule/algorithm/schema 版本、快照哈希与兼容矩阵；用单一 active pointer 原子激活，并设计请求租约、旧版本回收、历史追溯和回滚验证；区分 OLTP、在线只读快照和分析数据，禁止把 Redis 当权威数据源。
```

### Prompt 6：API 与契约
```text
设计 REST + OpenAPI 3.1 接口：鉴权、引用数据增量获取、位次反查、推荐提交/查询、草稿、志愿表、数据版本。为每个接口给出请求/响应、字段校验、状态码、Problem Details 错误体、ETag/If-None-Match、分页、超时、限流、缓存头和版本兼容策略。仅有副作用的写操作强制幂等键；推荐接口定义请求去重、同步转 202 异步的阈值、查询与取消语义。推荐结果必须返回 run_id、release_bundle_id、数据来源、置信度、降级记录、生成时间和免责声明；同时给出前端现有三接口的兼容迁移方案、OpenAPI breaking-change 检测和消费者契约测试。
```

### Prompt 7：缓存与防雪崩
```text
只设计缓存体系。列出引用数据、一分一段、院校专业、候选集、公共推荐计算结果、用户运行元数据、用户草稿分别能否缓存、缓存层级、Key、TTL、容量、失效方式和一致性要求。严禁在共享缓存中存放或复用可识别用户的画像、草稿和带身份推荐结果。对出分时热 Key、缓存穿透/击穿/雪崩、Redis 节点故障、版本切换、冷启动逐一给出预热、请求合并、单飞锁、布隆过滤器/空值、TTL 抖动、本地只读快照和降级方案，并输出缓存命中率与回源 QPS 的验收公式。
```

### Prompt 8：推荐引擎在线链路
```text
设计可在 1 秒内完成且可复现的推荐链路：离线构建省份/年份/科类/选科候选快照，在线做参数校验→release_bundle 锁定→硬过滤→等位分/计划修正→冲稳保垫→偏好打分→L1-L5 降级→解释生成→持久化。覆盖同分位次区间、批次和投档模式、专业组/代码跨年变更、征集志愿、专项计划、选科/体检/性别/语种限制、学费与校区、服从调剂、临时计划更正、填报截止时间。明确数据结构、算法复杂度、并行方式、超时预算、公共请求指纹与用户私有 run 元数据、CPU 隔离、过载时简化策略、可重放日志和算法灰度；绝不在一次请求中逐候选访问数据库。
```

### Prompt 9：数据管线与发布
```text
设计考试院/公开或授权来源数据的 ETL/ELT：建立官方来源优先级，原始文件落对象存储并校验哈希，解析、标准化、跨年院校/专业/专业组代码实体对齐、重复检测、跨表业务规则、异常隔离、质量评分、双人复核、黄金样例、省级对账、影子版本比对、抽样回放、审批、原子发布和回滚。输出 DAG、表与版本状态机、质量门禁、数据血缘、失败重试/死信、审计证据，以及“一分一段或招生计划缺失”时线上明确降级而非假精确的策略。
```

### Prompt 10：高可用、限流与容灾

## 8. 红队评审与收口提示词

```text
你现在是与原方案团队独立的首席架构评审人。不要重写方案，先寻找会在高考出分洪峰中导致宕机、数据错配、错误推荐或无法恢复的证据。按严重度列出：问题、触发条件、影响范围、现有防线为何不足、最小修复、验证实验。重点攻击同步扇出、数据库/Redis 热点、连接池、缓存版本污染、重试风暴、脑裂、消息重复、旧规则与新数据混用、跨用户越权和回滚不可用。最后给出“通过/有条件通过/拒绝”结论及阻断项。
```

## 9. 推荐执行顺序

1. 首轮：Prompt 0 + Prompt 1 + Prompt 2，得到可评审的总体方案。
2. 定型：至少运行 Prompt 3、5、7、8、10，解决容量、数据、缓存、推荐和容灾五个核心问题。
3. 工程化：运行 Prompt 6、9、11、12、13、14，补齐契约、管线、安全、运维和测试。
4. 决策：运行 Prompt 15；修复阻断项后再运行 Prompt 16。
5. 只有最终决策包通过后，才让 AI 按 ADR 和 OpenAPI 分批生成工程骨架、迁移脚本及测试，避免“边写代码边猜架构”。

## 10. 方案合格线

- 任一关键请求都能回答：数据版本是什么、是否命中缓存、访问了哪些依赖、超时后如何降级、结果能否复现。
- 任一组件故障都有检测、隔离、降级、恢复与演练；不存在未说明的单点。
- 30k RPS 不是口号：有流量模型、实例/连接/内存/带宽计算、压测脚本计划和明确通过门槛。
- 数据发布比代码发布更严格：有质量门禁、影子比对、原子切换、追溯和回滚。
- 高可用不以错误推荐为代价；没有可信数据时必须明确提示数据不可用或采用最后可信版本，绝不生成假精确结果。
